## Причины пропуска паролей

1. В 12 из 14 файлов имеется оболочка заказа: «Номер заказа», инструкция по разделителям, пример `Логин:Пароль`, маркер «Ваш заказ». Служебные строки ошибочно могли попадать в классификацию.
2. Для составных строк `email:секрет:ID:[JSON]:UA` прежний лексический анализатор не всегда включал режим деления по двоеточию, потому что почта находилась **до** первого двоеточия. Двоеточия внутри JSON/UA необходимо защищать.
3. Есть одна запись с переносами между троицей `email:секрет:ID:` и Cookie JSON; переносы не должны создавать отдельные аккаунты.
4. Вертикальный файл содержит блоки со множеством пустых строк, которые нужно группировать по признакам без переноса значений в соседние аккаунты.
5. В одном вертикальном блоке три адреса почты; без подтверждения не назначать недостающий пароль по смещённой позиции.
6. В составных `::` записях есть дополнительные статусы, примечания и URL. Не выдавать их за пароль.

## Исправления

- Маскировать только подтверждённую служебную оболочку заказа, сохраняя исходный текст и UTF-16 диапазоны значений.
- Распознавать строгий префикс `email:opaque:13–20-digit ID:Cookie JSON`, в том числе при переносе перед JSON.
- Назначать пароль аккаунта **с предупреждением** только при единственном кандидате и совпадении `c_user` в Cookie с внешним ID. Несовпадение блокирует назначение.
- Строгий разбор вертикальных блоков без автоматического угадывания секретов при лишних полях.
- Сохранять действующие TZ19 / подтверждённые схемы, приоритет подписей и ручного сопоставления.

## Приёмочные ограничения

- Нельзя считать отсутствие неразмеченных паролей ошибкой, если исходник неоднозначен.
- Для двух неподписанных секретов без надёжной структуры нужна ручная разметка или ранее подтверждённая схема.
- Не переписывать исходные Order-файлы и не отправлять их в GitHub.
- Не публиковать новый DMG без полного PASS Linux + macOS ARM64.
