# 3. IMPORT / CLASSIFIER — интеллектуальный разбор TXT

## 3.1. Цель

Переработать классификатор так, чтобы он распознавал данные по содержимому и структуре, а не только по позиции в строке или фиксированному разделителю.

Пользователь предоставил два тестовых файла:

- `Вставленный текст.txt`
- `Вставленный текст (2).txt`

Файлы имеют разную структуру, но содержат частично одинаковые типы полей.

Они являются примерами, а не исчерпывающим списком поддерживаемых форматов.

Файлы могут содержать реальные секреты авторизации. Не размещать оригиналы в репозитории, журналах, тестовых отчётах или артефактах сборки. Для автоматизированных испытаний создать обезличенные синтетические аналоги с такой же структурой.

## 3.2. Поддерживаемый ввод

- TXT;
- CSV;
- TSV;
- JSON;
- смешанные текстовые форматы;
- файлы без заголовков;
- записи с нестандартными разделителями;
- записи с многострочными значениями.

Максимальный входной размер — сохранить текущий лимит 50 MiB.

## 3.3. Особенности первого формата

Поддержать:

- разделитель `::`;
- дополнительные сегменты через `;`;
- многострочные записи;
- пустые значения;
- email;
- пароли;
- токены;
- User-Agent;
- массивы cookies JSON;
- числовые идентификаторы;
- даты рождения;
- GEO;
- URL изображений;
- дополнительные метки.

Не считать каждый перенос строки началом новой записи.

## 3.4. Особенности второго формата

Поддержать:

- разделитель `|`;
- пустые сегменты `||`;
- встроенный JSON-массив;
- Facebook URL;
- разные варианты User-Agent;
- значения после JSON;
- последовательности меток и значений.

Распознавать маркированные поля:

- `mail:`;
- `GEO`;
- `LIMIT`;
- `FP`;
- `AVA`;
- `DOC`;
- `sent`;
- `friend`.

Не воспринимать внутренние символы JSON и URL как разделители записи.

## 3.5. Основные поля

Сохранить существующие 11 полей:

1. `rowNumber`
2. `fullName`
3. `accountId`
4. `password`
5. `emailPassword`
6. `email`
7. `birthDate`

11. `cookies`

Добавить поддержку расширенных атрибутов:

- `twoFactorUrl`;
- `avatarUrl`;
- `documentUrl`;
- `limit`;

Неизвестные значения не удалять.

## 3.6. Алгоритм классификации

Реализовать последовательную обработку.

### Шаг 1. Определение кодировки

Поддерживать:

- UTF-8;
- UTF-8 с BOM;
- UTF-16LE/BE;
- Windows-1251;
- существующие возможности выбора кодировки.

При неоднозначной кодировке показывать предупреждение.

### Шаг 2. Выделение логических записей

Учитывать:

- кавычки;
- экранирование;
- вложенность JSON;
- переносы строк;
- разные разделители;
- пустые поля.

Выделять записи структурно. Не применять простое разделение по переводу строки как универсальный алгоритм.

### Шаг 3. Распознавание типов

Использовать признаки содержимого:

| Тип | Признак |
|---|---|
| Email | Корректная структура адреса |
| Дата рождения | Допустимая календарная дата |
| Facebook ID | Числовой идентификатор с достаточным контекстом |
| Facebook URL | Проверенный URL соответствующей площадки |
| User-Agent | Характерная структура идентификатора браузера |
| Cookies | Объект или массив cookie с определённой структурой |
| Access Token | Подтверждаемый контекст, не одна только длина строки |
| GEO | Название или код страны |
| AVA | URL изображения с соответствующей меткой |
| DOC | URL документа с соответствующей меткой |

Пароли могут не иметь уникального синтаксиса. Поэтому нельзя надёжно определить назначение каждого непрозрачного значения только регулярным выражением.

### Шаг 4. Контекстное сопоставление

Приоритет:

1. Явная метка поля.
2. Структурная схема, определённая с высокой уверенностью.
3. Формальная проверка значения.
4. Связанные поля и контекст.
5. Ручное подтверждение при неоднозначности.

### Шаг 5. Проверка конфликтов

Например, если идентификатор из Facebook URL не совпадает с идентификатором в данных cookie, показывать предупреждение `ACCOUNT_ID_CONFLICT`.

Не исправлять такие конфликты молча.

### Шаг 6. Результат

Каждая запись должна содержать:

- распознанные поля;
- исходное представление;
- информацию об уверенности;
- диагностические предупреждения;
- список неопознанных элементов;
- расположение значений в исходном файле.

## 3.7. Интерфейс

Добавить:

- автоматическое определение структуры;

- таблицу классификации;

## 3.8. Cookies и токены

Сохранять точность исходных значений.

Обязательные условия:

- Cookie выбранной строки копируется полностью.
- Копирование одной строки не затрагивает другую.
- Сортировка и фильтрация не изменяют привязку значений.

- Токены, пароли и cookies маскируются в диагностических журналах.
- Данные не отправляются внешним сервисам.
- Импортированные секреты не используются для автоматического входа в Facebook или подмены сессий.

# 4. FACEBOOK CHECKER — доработка проверки аккаунтов

## 4.1. Проблема

Существующий Checker не всегда показывает информацию об аккаунтах и может возвращать `NETWORK_FAILURE`.

Необходимо исправить диагностическую часть, улучшить представление результатов и расширить поддержку разрешённых источников информации.

## 4.2. Входные данные

Поддержать:

- один Facebook ID;
- ссылку на профиль;
- список ID;
- список ссылок;
- смешанный список.

Максимум 100 целей за одну операцию.

Нормализовать входные значения, удалять дубли, сохранять соответствие исходной записи и результата.

## 4.3. Отображаемая информация

Для каждого аккаунта предусмотреть:

- ID;
- URL;
- имя, если получено из разрешённого источника;
- изображение профиля, если доступно;
- тип объекта, если достоверно определён;
- статус доступности;
- причину ошибки;
- дату и время проверки;
- источник сведений;
- копирование отдельных значений.

## 4.4. Статусы

Использовать:

- `PROFILE_VISIBLE`;
- `UNAVAILABLE`;
- `LOGIN_REQUIRED`;
- `CHALLENGE_REQUIRED`;
- `RATE_LIMITED`;
- `NETWORK_ERROR`;
- `UNKNOWN`;
- `CANCELLED`.

Нельзя автоматически считать HTTP 403/404 или недоступность страницы доказательством блокировки аккаунта.

Проверка только по ID без разрешённой авторизации может не предоставлять сведения о профиле.

Необходимо различать:

- данные, введённые пользователем;
- данные, извлечённые из локального файла;
- данные, подтверждённые Facebook;
- предположения, которые невозможно подтвердить.

## 4.5. Источники

Проверить разрешённые возможности Meta Graph API.

Использовать API только при наличии соответствующего доступа и разрешений.

Не использовать импортированные пароли, cookies или токены для автоматической авторизации.

Не реализовывать обход защитных проверок Facebook, CAPTCHA, checkpoint или ограничений доступа.

## 4.6. Интерфейс и очередь

Добавить:

- понятную таблицу результатов;
- индикатор прогресса;
- отмену проверки;
- повторную проверку одного аккаунта;
- сортировку;
- фильтрацию по статусу;
- копирование ID и ссылки;
- подробную диагностику ошибок;
- отображение времени последней проверки.

Соблюдать ограничения частоты запросов, `Retry-After`, тайм-ауты и корректное прекращение проверки.

Главное требование: **вместо пустого результата отображать фактическую причину отсутствия данных**.

# 7. PHOTOS — автоматическая генерация GEO по стране и городу

## 7.1. Основной сценарий

Вместо обязательного ручного ввода Latitude и Longitude реализовать простой интерфейс:

**Страна → Город → Генерировать GEO**

Пример:

- Страна: Италия.
- Город: Милан.
- Загружено: 100 фотографий.
- Действие: «Генерировать GEO».

BLEGO должен создать для каждой фотографии собственные координаты в пределах Милана.

## 7.2. Единый режим распределения

**Оставить только один режим — случайное распределение по всей территории города.**

Не добавлять:

- выбор радиуса;
- минимальный разброс;
- небольшой разброс;
- средний разброс;
- ограничение радиусом вокруг базовой точки;
- переключатель разных режимов распределения.

Все эти варианты исключены из окончательного ТЗ.

## 7.3. Географические границы

Для генерации использовать реальные географические границы города.

Поддерживать:

- Polygon;
- MultiPolygon;
- внутренние исключённые области;
- сложные границы;
- отрицательные координаты;
- разные географические широты.

Источники данных могут включать OpenStreetMap или другие лицензированные географические наборы с достаточным покрытием.

Обязательно документировать источник, версию и лицензию.

Не использовать произвольный квадрат или окружность вокруг центра города как замену его реальных границ.

## 7.4. Алгоритм

1. Пользователь выбирает страну.
2. Приложение показывает подходящие города.
3. Пользователь выбирает город.
4. Приложение загружает или получает из кэша географический контур.
5. Проверяет корректность контура.
6. Создаёт отдельную случайную GPS-точку для каждой фотографии.
7. Проверяет попадание каждой точки внутрь границ.
8. Проверяет уникальность координат в рамках операции.
9. Сохраняет результаты в плане изменений.
10. Передаёт результаты на интерактивную карту.
11. Записывает координаты только после подтверждения экспорта.

Выбор точек выполнять с равномерным распределением по площади допустимой территории, используя подходящую картографическую проекцию или площадь геометрических элементов.

Применять криптографически стойкий генератор случайных чисел.

Учитывать точность координат при записи EXIF. Уникальность должна проверяться с учётом фактической точности хранения, а не только исходных чисел с плавающей точкой.

## 7.5. Географическая корректность

Требования:

- все точки внутри выбранного города;
- не выдавать координаты соседнего города;
- не использовать некорректную геометрию;
- не генерировать данные без доступной проверенной границы;
- корректно работать с внутренними исключёнными территориями;
- исключать случайное изменение исходного GEO при отмене;
- не пересчитывать точки без явного действия.

Если границы недоступны, показывать `GEO_BOUNDARY_UNAVAILABLE`.

## 7.6. Регенерация

Добавить кнопку **«Перегенерировать GEO»**.

Она должна создавать новый набор координат для выбранных фотографий.

Дополнительно разрешить перегенерацию одной фотографии.

После генерации координаты должны оставаться неизменными до следующего явного действия.

## 7.7. Ручное перемещение

Сохранить возможность вручную указать точные координаты через дополнительные элементы интерфейса.

При использовании интерактивной карты разрешить перемещение маркера выбранной фотографии.

В режиме выбранного города точка должна оставаться внутри его географических границ.

При необходимости пользователь может выбрать другой город или воспользоваться отдельным режимом точных ручных координат.

## 7.8. Высота

Altitude оставить необязательным.

Не генерировать случайную высоту без достоверного источника.

По умолчанию не изменять высоту, если пользователь этого не запросил.

# 8. PHOTOS — интерактивная карта

## 8.1. Общая задача

Добавить интерактивную карту непосредственно в раздел Photos.

Карта должна отображать исходное и новое местоположение фотографий.

При выборе другого GEO пользователь должен видеть результат перемещения точек до физической записи метаданных.

## 8.2. Предлагаемая технология

Использовать MapLibre GL JS либо технически обоснованную альтернативу с открытым и подходящим для Electron механизмом отображения.

Для геометрии использовать GeoJSON или совместимый формат.

Карта должна работать в архитектуре Electron без предоставления renderer прямого доступа к файловой системе.

## 8.3. Исходные координаты

После загрузки фотографий приложение считывает GPS через существующий движок ExifTool.

Если фотография содержит GPS, на карте появляется точка её местоположения.

Если GPS отсутствует, фотография попадает в группу **«Без GEO»**.

Не размещать фотографии без GPS в произвольной точке карты.

## 8.4. Новые координаты

После выбора страны и города и нажатия «Генерировать GEO»:

- карта показывает новую область;
- для каждой фотографии отображается новая точка;
- новые точки соответствуют заранее вычисленным координатам;
- изменения не записываются в файлы до подтверждения.

## 8.5. Сравнение «До / После»

Добавить переключатель:

**До | После**

Режим «До»:

- исходные координаты;
- отсутствие точки для изображений без GPS.

Режим «После»:

- новые сгенерированные координаты;
- отображение всех изображений, для которых сформирован GEO.

Предусмотреть визуальное различие между исходными и новыми координатами.

## 8.6. Анимация перемещения

При переключении допустима плавная анимация перемещения точек.

Анимация должна:

- не блокировать интерфейс;
- не менять фактические значения координат;
- не нарушать работу при большом количестве фотографий;
- корректно работать при переходе между удалёнными городами и странами.

При большой географической дистанции предпочтительнее сначала перестроить область карты, а затем показать новые точки, чем анимировать маркеры через весь земной шар.

## 8.7. Выбор фотографии

При нажатии на точку показывать:

- миниатюру;
- имя файла;
- исходные координаты;
- новые координаты;
- статус обработки.

При выборе фотографии в списке соответствующая точка подсвечивается на карте.

## 8.8. Массовые точки

Поддержать:

- 10 фотографий;
- 100 фотографий;
- 500 фотографий;
- 1000 фотографий.

Для близко расположенных точек использовать группировку маркеров при мелком масштабе.

При приближении карты группа должна раскрываться в отдельные точки.

Не допускать зависаний при большом количестве маркеров.

## 8.9. Работа с картографическими источниками

Использовать источник картографических слоёв с условиями, совместимыми с предполагаемым использованием BLEGO.

Не внедрять незаконное массовое скачивание тайлов.

Сетевая загрузка карты допускается только после явного разрешения пользователя.

Не отправлять фотографии или их исходные метаданные поставщику картографических слоёв.

Если источник тайлов недоступен, приложение должно по возможности отображать доступные локальные контуры и точки, либо показывать понятное сообщение об отсутствии картографической подложки.

Работа с фотографиями и экспорт не должны зависеть от доступности фоновой карты после получения необходимых географических границ.

## 8.10. Адаптивность карты

При уменьшении окна:

- карта становится компактнее;
- панели управления перестраиваются;
- кнопки не перекрывают маркеры;
- список файлов переносится ниже карты;
- остаётся возможность масштабирования и выбора точки;
- сохраняется доступ к кнопке экспорта.

## 9.2. Запись GPS

- GPSLatitude;
- GPSLongitude;

Учитывать отрицательные значения и нулевые координаты.

Сохранять выбранные дату, время и часовой пояс, если пользователь не менял их.

Не генерировать скрытые значения вместо пустых.

## 9.3. Проверка результата

1. Повторно открыть копию.

5. Проверить сохранность остальных метаданных в пределах существующего контракта.
6. Проверить целостность оригинала.
7. Зафиксировать результат.

## 9.4. Экспорт папок

При загрузке папок предусмотреть сохранение их относительной структуры в выходном каталоге.

Требования:

- не выходить за пределы выбранной папки экспорта;
- не перезаписывать существующие файлы;
- корректно обрабатывать одинаковые имена;
- сохранять связь оригинал → копия;
- показывать прогресс;
- поддерживать отмену;
- формировать итоговый отчёт;
- разрешать повторную обработку ошибок.

## 9.5. Масштабирование

Проверить пакеты:

- 1 фото;
- 10 фото;
- 100 фото;
- 500 фото;
- 1000 фото.

Отдельно испытать реальные фотографии высокого разрешения и смешанные форматы.

Не считать успешную обработку маленьких синтетических изображений полноценной проверкой производительности на реальных фотографиях.

# 10. АДАПТИВНЫЙ ИНТЕРФЕЙС

Примеры целевой ширины:

| Рабочая ширина экрана | 1/3 ширины |
|---|---:|
| 1280 px | ~427 px |
| 1440 px | 480 px |
| 1512 px | 504 px |
| 1728 px | 576 px |

Размеры считать по фактической рабочей области, а не по физическому количеству пикселей дисплея Retina.

## 10.2. Ограничения Electron

Пересмотреть текущие `minWidth` и `minHeight` в `electron/main.cjs`.

Текущее ограничение минимальной ширины препятствует уменьшению окна до требуемых размеров.

Предусмотреть минимальную рабочую ширину порядка 360–390 CSS-пикселей, если это допускается оконным менеджером и результатом интерфейсной приёмки.

Изменение размера — обычным перетаскиванием границы окна.

Не выполнять масштабирование всего приложения через `transform: scale()`.

## 10.3. Боковая панель

При уменьшении окна автоматически переходить в компактный режим.

Обычный режим:

- логотип;

- иконки;
- индикатор локального режима;

Компактный режим:

- узкая боковая панель;

- визуальное выделение активного раздела;

- доступная навигация с клавиатуры.

Не допускать обрезания иконок.

## 10.4. Нижний блок

Исправить адаптивность:

- `Local workspace · no account`;
- зелёного индикатора;
- `powered by blemish&alterego`.

При компактном режиме длинные подписи можно скрывать, но индикатор должен оставаться понятным через всплывающую подсказку и доступное название.

В развёрнутом режиме показывать полные подписи.

Не допускать переноса слов по отдельным буквам.

## 10.5. Адаптивность разделов

- Generator;
- Import;
- News;
- Network;
- Photos;
- Friends;
- Checker;
- Settings;
- Archive.

Требования:

- карточки перестраиваются в одну колонку;
