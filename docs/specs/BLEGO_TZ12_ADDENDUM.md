# Дополнение к ТЗ №12
## 21. Оптимизация разработки и тестирования — выборочная регрессия

**Приоритет:** P1  
**Цель:** сократить время выполнения задач, вычислительные затраты и количество избыточных тестов без ухудшения качества BLEGO.

### 21.1. Основной принцип

**Не требуется повторно запускать полный набор тестов всего приложения после каждого изменения, если оно не затрагивает остальные компоненты.**

Codex должен использовать выборочное тестирование на основании анализа изменённых файлов, зависимостей и потенциального влияния на другие модули.

Это требование имеет приоритет над предыдущими указаниями ТЗ №12 об обязательном полном прогоне после каждого этапа.

### 21.2. Анализ влияния изменений

Перед тестированием исполнитель должен:

1. Получить список изменённых файлов через `git diff`.
2. Определить модули, которым принадлежат изменения.
3. Проверить прямые и косвенные зависимости.
4. Определить связанные модульные, интеграционные и интерфейсные тесты.
5. Запустить только необходимую группу проверок.
6. Зафиксировать, какие проверки не запускались и почему.

Если область влияния нельзя достоверно определить, выполнять расширенную регрессию.

### 21.3. Матрица выборочного тестирования

| Изменённый компонент | Обязательные проверки |
|---|---|
| News HTML/CSS | News GUI, копирование, адаптивность, визуальное сравнение |
| BIO HTML/CSS | BIO GUI, селекторы, копирование, визуальное сравнение |
| Словари ФП | Валидация словарей, генерация ФП, уникальность, локализация |
| Общие CSS-компоненты | Все экраны, использующие изменённые стили |
| Генератор ФП | Generator unit/integration и связанные GUI |
| Общее хранение данных | Интеграционные тесты всех затронутых модулей |
| Electron IPC / preload | Связанные интеграционные и GUI-тесты |
| Общие зависимости | Расширенная регрессия зависимых модулей |
| Нативная упаковка | Проверка установки и запуска приложения |

Неизменённые и независимые компоненты можно не тестировать повторно.

### 21.4. Уровни тестирования

**Уровень 1 — минимальный**

Для локальных изменений ресурсов, словарей и стилей.

Выполнить проверки корректности данных, затронутые модульные тесты и необходимые визуальные проверки.

**Уровень 2 — выборочный**

Для изменений логики отдельных компонентов.

Выполнить относящиеся к ним unit, integration и GUI-тесты.

**Уровень 3 — расширенный**

Для изменений общих компонентов, IPC, SQLite, глобальных CSS, архитектуры или зависимостей.

Выполнить тесты всех потенциально затронутых разделов.

**Уровень 4 — полный**

Для крупных архитектурных изменений, неопределённой области влияния, накопленных изменений без достаточного покрытия либо окончательной приёмки коммерческого релиза.

Выполнить полный набор проверок BLEGO.

### 21.5. Оптимизация macOS QA

Не пересобирать DMG после каждого небольшого изменения.

Промежуточные исправления сначала проверять локально или через подходящие CI-тесты.

Создавать установочную QA-сборку после объединения связанных изменений в проверенный кандидат.

Если готовится новый установочный ZIP, обязательно проверить:

- Успешную сборку.
- Запуск установленного приложения.
- Отсутствие критических ошибок загрузки.
- Основные сценарии изменённых компонентов.
- Контрольные суммы файлов.

Полный GUI-прогон всех разделов при каждой промежуточной сборке не требуется, если анализ влияния подтверждает отсутствие затрагивающих их изменений.

### 21.6. Оптимизация работы Codex

Исполнитель должен:

1. Группировать логически связанные изменения.
2. Избегать повторного анализа неизменённых файлов.
3. Не запускать одинаковые тесты без изменений кода или окружения.
4. Повторно использовать результаты проверок неизменённого коммита.
5. Использовать кэш зависимостей и сборки при возможности.
6. Выполнять целевые тесты сразу после изменения компонента.
7. Запускать расширенную регрессию только при выявленном риске.
8. Не собирать DMG до завершения основных изменений.
9. Не создавать повторные отчёты, дублирующие прежние результаты.
10. Не запускать ресурсоёмкие стресс-тесты без связи с изменённой функциональностью.

### 21.7. Правила безопасности

Выборочная регрессия не должна приводить к сокрытию ошибок.

Запрещено:

- Отключать тесты ради успешного результата.
- Удалять неуспешные тесты.
- Изменять ожидаемые результаты без обоснования.
- Объявлять непройденные тесты успешными.
- Игнорировать зависимости изменённых компонентов.
- Использовать старый PASS как доказательство проверки нового кода, если изменение могло повлиять на тестируемую функциональность.

### 21.8. Отчётность

В итоговом отчёте представить:

| Модуль | Изменён | Проверка | Статус |
|---|---|---|---|
| News | Да | Выборочные GUI и визуальные | PASS / FAIL |
| BIO | Да | Выборочные GUI и integration | PASS / FAIL |
| Пулы ФП | Да | Валидация и генерация | PASS / FAIL |
| Network | Нет | Не запускалась при подтверждённой независимости | NOT RUN |
| Facebook Checker | Нет | Не запускалась при подтверждённой независимости | NOT RUN |
| Photos | Нет | Не запускалась при подтверждённой независимости | NOT RUN |

Статус `NOT RUN` не равен `PASS`.

Для каждой пропущенной группы тестов указывать короткое техническое обоснование.

### 21.9. Критерий приёмки

Выборочное тестирование считается достаточным, если:

- Проверены все изменённые компоненты.
- Проверены потенциально затронутые зависимости.
- Не обнаружены необъяснённые регрессии.
- Пропущенные проверки документированы.
- Установочная сборка проверена, если она создавалась.
- Оставшиеся ограничения явно указаны.

**Итоговое требование:** Codex должен стремиться к минимальному достаточному объёму тестирования, обеспечивающему уверенность в корректности внесённых изменений, а не к максимальному количеству повторных прогонов.
