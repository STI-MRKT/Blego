# 1. NETWORK — IP Trust включён по умолчанию

**Приоритет: P1**

## 1.1. Задача

Сейчас в разделе Network имеется переключатель:

`Check IP Trust: send exit IP to proxycheck.io`

Необходимо убрать его из основного интерфейса.

Проверка IP Trust должна быть включена по умолчанию при выполнении проверки прокси.

## 1.2. Требуемая логика

При проверке прокси BLEGO должен:

1. Проверить доступность соединения.
2. Определить выходной IP.
3. При наличии разрешения на внешний запрос выполнить проверку репутации через `proxycheck.io`.
4. Рассчитать IP Trust на основании фактического ответа провайдера.
5. Показать результат цветным индикатором.
6. Отдельно показать Connection Quality.

Не требовать повторного включения переключателя при каждой проверке.

## 1.3. Изменение интерфейса

Полностью убрать из основного экрана:

- переключатель Check IP Trust;
- подпись `send exit IP to proxycheck.io`;
- занимаемое переключателем пустое пространство.

Оставить:

- поле Proxy;
- Check Proxy;
- Check with Speed;
- Exit IP;
- Connection Status;
- Connection Quality;
- IP Trust;
- цветные шкалы;
- отображение скорости;
- сообщения об ошибках.

## 1.4. Прозрачность внешних запросов

Поскольку `proxycheck.io` является сторонним сервисом, перед первым включением проверки репутации необходимо предоставить понятное уведомление о передаче выходного IP.

После согласия пользователя дополнительные переключатели на основном экране не нужны.

Если согласие не предоставлено, внешний запрос не выполнять, а результат показывать как `N/A`.

Не передавать логины и пароли прокси.

Не отправлять полный адрес прокси, если провайдеру необходим только выходной IP.

## 1.5. Обработка ошибок

При недоступности провайдера, превышении лимита или некорректном ответе показывать:

`IP Trust: N/A`

Не подменять отсутствие данных оценкой 0 или 100.

Оставить рабочей обычную проверку прокси даже при недоступном API репутации.

## 1.6. Техническая проверка

Начать с:

- `src/js/ui/network.js`;
- `src/js/main.js`;
- `src/js/state.js`;
- существующего сервиса проверки прокси.

Проверить обработчик `proxy-reputation` и связанные значения состояния.

Убрать зависимость фактической проверки от удалённого визуального переключателя.

## 1.7. Приёмка

- Переключателя нет в интерфейсе.
- После разрешения IP Trust проверяется автоматически.
- Фактический ответ провайдера отображается корректно.
- При ошибке провайдера используется N/A.
- Connection Quality работает независимо.
- Не возникает скрытой передачи учётных данных.
- Интерфейс корректен на узком окне.

Не ограничиваться скрытием текста через CSS — соответствующие блоки не должны занимать место в разметке.

Эти механизмы должны продолжать работать.

Если экспорт неуспешен, необходимо показывать конкретную ошибку.

В случае частичной ошибки разрешить повторную обработку неуспешных фотографий, но без постоянного блока `Retry selected files`. Предлагать действие только при фактической ошибке.

## 2.6. Дополнительные параметры

# 3. FACEBOOK CHECKER — реальная проверка публичного содержимого

**Приоритет: P0 — критический дефект**

## 3.1. Проблема

Checker продолжает возвращать `UNKNOWN`, `INSUFFICIENT_EVIDENCE` либо ошибки соединения.

Пользователь не получает полезного результата о доступности публичной страницы.

Необходимо исследовать и исправить причины, по которым приложение не может интерпретировать разрешённые публичные ответы Facebook.

## 3.2. Задача

Проверять фактическую публичную доступность Facebook-профиля по:

- числовому ID;
- URL профиля;
- списку ID;
- списку URL.

Сохранить массовую проверку до 100 целей.

## 3.3. Основные статусы

### ACTIVE

Возвращать, когда:

- получен успешный ответ;
- загружен содержательный публичный контент;
- подтверждено соответствие запрошенному профилю;
- ответ не является страницей входа или защитной проверкой.

Одного HTTP 200 недостаточно.

### BLOCKED

Возвращать, когда Facebook явно сообщает о недоступности публичного содержимого проверяемой страницы.

Примеры:

- Content isn't available.
- This page isn't available.
- Другой достоверно распознанный ответ о недоступности целевого профиля.

**BLOCKED означает недоступность публичного содержимого, а не доказательство санкций в отношении аккаунта.**

### Прочие статусы

Сохранить отдельные состояния:

- LOGIN_REQUIRED;
- CHALLENGE_REQUIRED;
- RATE_LIMITED;
- NETWORK_ERROR;
- UNKNOWN;
- CANCELLED.

Нельзя выдавать BLOCKED только по тайм-ауту, сетевой ошибке или необходимости авторизации.

## 3.4. Анализ существующего механизма

Проверить:

- `electron/features/facebook/inspect.cjs`;
- `electron/features/facebook/service.cjs`;
- `electron/features/facebook/transport.cjs`;
- `electron/features/facebook/diagnostics.cjs`;
- `src/js/ui/checker.js`.

Определить, почему публичный ответ не преобразуется в полезный результат.

Проверить:

1. DNS и сетевое соединение.
2. TLS.
3. Перенаправления.
4. Сжатие ответа.
5. Кодировку HTML.
6. Ограничения размера ответа.
7. Страницы входа.
8. Страницы недоступности.
9. Динамически загружаемое содержимое.
10. Соответствие контента запрошенному профилю.
11. Обработку отсутствующих HTML-метаданных.

## 3.5. Получение реального содержимого

Использовать разрешённые способы доступа к публичным страницам.

Если обычный сетевой запрос получает только промежуточную страницу, исследовать технически допустимый способ отображения общедоступного ресурса.

Реализация не должна:

- обходить CAPTCHA;
- обходить checkpoint;
- подменять сессии;
- использовать импортированные cookies для входа;
- использовать чужие Access Token;
- обходить ограничения Meta.

Если платформа не предоставляет доступ к данным, возвращать точную причину и UNKNOWN, а не выдумывать результат.

## 3.6. Улучшение диагностики

В подробностях каждой проверки показывать:

- исходный ID или URL;
- нормализованный URL;
- HTTP-статус;
- время проверки;
- итоговый статус;
- код причины;
- краткое пользовательское объяснение.

Не раскрывать конфиденциальные значения и не сохранять полный HTML страницы без необходимости.

## 3.7. Реальные испытания

Провести проверку на разрешённых реальных публичных целях:

1. Известная публичная страница, доступная без авторизации.
2. Страница с подтверждённым сообщением о недоступности, если такая тестовая цель доступна.
3. Публичный профиль с ограниченным содержимым.
4. Случай, когда Facebook требует вход.
5. Сетевой отказ.

Также выполнить контролируемые тесты HTML-ответов.

Для каждой проверки фиксировать фактические доказательства результата.

**Не считать работу с искусственным HTML достаточным доказательством исправления реального Facebook Checker.**

Если реальная положительная проверка блокируется политикой или техническими ограничениями Meta, указывать BLOCKED для соответствующего пункта приёмки, а не PASS.

## 3.8. Интерфейс

Заменить техническое описание Checker на:

«Проверка доступности Facebook-профилей».

ACTIVE отображать зелёным.

BLOCKED отображать красным.

UNKNOWN и сетевые ошибки — нейтральным цветом.

Сохранить:

- массовый ввод;
- поиск;
- повторную проверку;
- сортировку;
- фильтрацию;
- копирование ID и URL.

# 4. CLASSIFIER — улучшение разбора TXT с переменными разделителями

**Приоритет: P0 — критический дефект распознавания**

## 4.1. Проблема

Классификатор некорректно извлекает некоторые поля, особенно пароли и электронную почту, когда записи используют нестандартные разделители.

Необходимо расширить обработку и распознавание структуры.

## 4.2. Поддерживаемые варианты

### Формат A — смешанные разделители

```text
почта :: Token :: User-Agent :: :: [{json cookie}] :: пароль :: почта;пароль;пароль почты;день рождения;ID;ФИО
```

### Формат B — двоеточия

```text
логин:пароль:электронная почта:пароль почты:2FA-код:идентификатор профиля
```

### Формат C — вертикальные черты

```text
Логин | Пароль | ID | Cookie | UserAgent
```

### Дополнительные варианты

Поддержать:

- `:`
- `::`
- `;`
- `|`
- `/`
- `\\`
- переносы строк;
- смешение разных разделителей;
- пустые сегменты;
- записи без заголовков.

Символы `/` и `\\` рассматривать как потенциальные разделители только при подтверждении структуры записи.

Не делить URL, JSON, User-Agent, пути файлов и другие составные значения по их внутренним символам.

## 4.3. Алгоритм обработки

Рекомендуемая последовательность:

**Этап 1 — определение кодировки.**

Сохранить поддержку существующих форматов кодировок.

**Этап 2 — выделение логических записей.**

Учитывать вложенные JSON-объекты и массивы, кавычки, экранирование и многострочные значения.

**Этап 3 — определение разделителей.**

Анализировать потенциальные разделители на верхнем уровне структуры.

Не применять безусловное `split(':')` или `split('/')` ко всему тексту.

**Этап 4 — распознавание типов.**

Определять:

- логин;
- ID;
- ФИО;
- основную почту;
- резервную почту;
- пароль аккаунта;
- пароль почты;
- 2FA-код;
- Access Token;
- User-Agent;
- cookies;
- GEO;
- дату рождения;
- дополнительные метки.

**Этап 5 — контекстный анализ.**

Использовать соседние поля и повторяющуюся структуру записей.

**Этап 6 — проверка конфликтов.**

Не назначать значения произвольно.

**Этап 7 — формирование результата.**

Сохранять исходные значения, диагностические сведения и возможность ручного уточнения.

## 4.4. Улучшение распознавания паролей

Добавить явные правила для:

- password;
- pass;
- пароль;
- mail password;
- email password;
- пароль почты;
- пароль от почты;
- recovery email;
- backup email.

Разделять основной пароль и пароль почты.

Использовать подтверждённую схему, если записи одного файла повторяются в одинаковом формате.

Не считать случайную последовательность символов паролем исключительно по длине или наличию специальных символов.

Не создавать вымышленные пароли, если поле отсутствует.

## 4.5. Поддержка 2FA

Добавить распознавание отдельно обозначенного 2FA-кода в пределах записи.

Не смешивать код с:

- паролем;
- идентификатором профиля;
- ссылкой на настройки 2FA;
- токеном доступа.

Не использовать распознанные коды для авторизации.

2FA-коды считать конфиденциальными и не включать в обычный семипольный экспорт и архив без отдельного согласования.

## 4.6. Контекст всего файла

Разработать механизм выявления повторяющихся структур.

Если несколько записей имеют совместимую схему, использовать её для уточнения неоднозначных значений.

При этом:

- не смешивать записи разных схем;
- не переносить данные между аккаунтами;
- учитывать пустые значения;
- сохранять исходную последовательность;
- не назначать неоднозначные поля без достаточных оснований.

## 4.7. Мусорный текст

В начале и между полезными записями могут находиться русские и английские пояснения.

Не превращать такие строки в пустые профили.

Не отбрасывать полезные записи только потому, что в них отсутствует одно из ожидаемых полей.

## 4.8. Исходный текст

Сохранять точный исходный текст каждого распознанного значения.

Особенно важно для:

- cookies;
- User-Agent;
- токенов;
- паролей;
- длинных строк.

Не выполнять неявное изменение значений при классификации.

## 4.9. Пользовательский интерфейс

Сохранить существующую таблицу и отдельные кнопки копирования.

Не возвращать технические статусы, ранее удалённые из основного интерфейса.

Не возвращать общую верхнюю кнопку «Копировать».

Сохранить:

- ручное уточнение;
- поиск;

## 4.10. Испытания

Создать размеченные синтетические наборы для всех форматов.

Минимальные сценарии:

1. Полная запись с разделителем `::`.
2. Запись с разделителем `:`.
3. Запись с разделителем `|`.
4. Запись со смешанными разделителями.
5. Запись со слэшем.
6. Запись с обратным слэшем.
7. Запись с вложенным JSON.
8. User-Agent с символами-разделителями.
9. URL с `https://`.
10. Пустые поля.
11. Несколько email.
12. Два разных пароля.
13. 2FA-код.
14. Отсутствующий пароль почты.
15. Неоднозначное непрозрачное значение.
16. Мусорный текст перед записями.
17. Несколько записей на одной строке.
18. Одна запись на нескольких строках.
19. Разные структуры внутри одного файла.
20. Конфликт идентификаторов.

Для размеченных наборов измерять точность, полноту и ложные назначения.

**Критерий:** все однозначно определяемые значения должны правильно классифицироваться, а неоднозначные не должны получать выдуманное назначение.

Не использовать импортированные секреты для входа в аккаунты.

# 5. GENERATOR / BIO — отдельное отображение города организации

**Приоритет: P2 — интерфейс и представление данных**

## 5.1. Проблема

Сейчас название компании или учебного заведения объединено с названием города.

Например:

`Ralph Lauren Corporation — New York`

`Columbia University — New York`

`Stuyvesant High School — New York`

Это неудобно для копирования.

## 5.2. Новое представление

Название организации и её город должны отображаться отдельно.

### Место работы

**Организация:**

`Ralph Lauren Corporation`

**Город:**

`New York`

### Университет

**Учебное заведение:**

`Columbia University`

**Город:**

`New York`

### Средняя школа

**Учебное заведение:**

`Stuyvesant High School`

**Город:**

`New York`

## 5.3. Кнопки копирования

Для каждого значения предусмотреть собственную кнопку.

Копирование названия организации должно возвращать только её официальное название.

Копирование города — только название города.

Не добавлять символ `—` или дополнительные подписи.

Не копировать сразу оба поля по нажатию одной кнопки.

## 5.4. Хранение данных

Предпочтительно хранить структурированные значения:

```text
employer.name
employer.city

university.name
university.city

school.name
school.city
```

Либо использовать существующую модель с отдельными полями местоположения.

Не полагаться исключительно на разделение готовой строки по тире.

Некоторые официальные названия сами содержат название города, например New York University. Нельзя ошибочно обрезать часть настоящего названия.

Сохранять идентификатор организации и данные справочника, если они уже присутствуют во внутренней модели.

## 5.5. Автоматическое заполнение

При генерации BIO автоматически:

1. Выбрать организацию из реального справочника.
2. Заполнить её название.
3. Заполнить её фактический город.
4. Отобразить значения раздельно.
5. Сохранить их автоматически.

Если организация находится в другом городе региона, показывать её реальное местоположение, а не город выбранного профиля.

## 5.6. Перегенерация

При повторном подборе организации одновременно обновлять название и соответствующий город.

Не менять несвязанные BIO-поля.

После ручного изменения сохранить данные автоматически.

## 5.7. Совместимость

Ранее созданные BIO могут содержать объединённые строки.

Предусмотреть безопасное открытие таких записей.

Если название и город можно достоверно сопоставить со справочником, представить их раздельно.

Если нет — сохранить исходное название полностью и оставить город незаполненным.

Не удалять исторические BIO и не повреждать архив.

## 5.8. Проверки

- Раздельное копирование работодателя и города.
- Раздельное копирование университета и города.
- Раздельное копирование школы и города.
- Правильный город после повторной генерации.
- Сохранение после перезапуска.
- Корректное открытие старого BIO.
- Отсутствие потери части официального названия.
- Работа на узком окне BLEGO.

# 11. Критерии окончательной приёмки

### Network

Переключатель IP Trust отсутствует. После разрешения внешний запрос репутации выполняется автоматически при проверке прокси. Результаты отображаются корректно.

### Photos

Основной экран не перегружен техническими панелями. Пользователь может загрузить фото, изменить GEO, увидеть карту и безопасно сохранить копии без дополнительного Preview changes.

### Facebook Checker

Приложение получает и анализирует реальные разрешённые публичные ответы. ACTIVE и BLOCKED присваиваются только при достаточных доказательствах, а отсутствие данных и ошибки сети не подменяются ложными результатами.

### Classifier

Поддерживаются разные разделители и их комбинации. Пароли, почты, ID, 2FA и остальные значения корректно распознаются при однозначной структуре. Исходные данные не теряются.

### BIO

Название работодателя, университета или школы и их фактический город отображаются раздельно и копируются отдельными кнопками. Старые записи остаются доступными.

### Регрессия

Все ранее проходившие автоматизированные проверки продолжают проходить. Критических регрессий в Friends, News, ФП, Архиве и Photos нет.

### Установка

Установленное приложение проверено на macOS ARM64. Контрольные суммы подтверждены. Статус подписи Apple указан.
