# 4. NETWORK / PROXY — цветные индикаторы качества

## 4.1. Цель

Сделать качество прокси визуально понятным без необходимости анализировать множество числовых параметров.

Добавить две отдельные горизонтальные шкалы:

- **Connection Quality**
- **IP Trust**

Каждая шкала показывает оценку от 0 до 100.

## 4.2. Цветовая шкала

Использовать плавный переход:

**Красный → Оранжевый → Жёлтый → Салатовый → Зелёный.**

Низкие значения означают неудовлетворительный результат, высокие — более благоприятный.

Пример условной шкалы:

- 0–20: красный;
- 21–40: оранжевый;
- 41–60: жёлтый;
- 61–80: светло-зелёный;
- 81–100: зелёный.

Конкретные границы согласовать с существующей формулой BLEGO и документировать.

## 4.3. Достоверность

Не смешивать локальное качество соединения и репутацию IP.

Connection Quality основывается на фактических сетевых измерениях.

IP Trust — на доступных репутационных данных, если провайдер вернул валидный результат.

Если результат неизвестен, показывать нейтральную серую шкалу и значение `N/A`.

Не подменять отсутствие ответа провайдера оценкой 0 или 100.

Сохранить реальные числовые значения для пользователей, которым они нужны.

# 12. FACEBOOK CHECKER — критическое исправление

**Приоритет P0.**

## 12.1. Проблема

Facebook Checker по-прежнему не предоставляет полезного результата при проверке аккаунтов.

Необходимо исправить фактическую проверку публичной страницы.

## 12.2. Принцип работы

Пользователь вводит:

- Facebook ID;
- ссылку на профиль;
- список ID;
- список ссылок.

Checker нормализует цель и выполняет запрос к разрешённой публичной странице Facebook.

Проверка должна определять, доступен ли содержательный контент именно запрошенного профиля.

Не ограничиваться:

- проверкой корректности ссылки;
- наличием HTTP 200;
- наличием HTML-страницы входа;
- формальным подтверждением существования домена Facebook.

## 12.3. Алгоритм

1. Нормализовать ID или URL.
2. Определить безопасный адрес публичного профиля.
3. Выполнить ограниченный по времени запрос.
4. Проверить перенаправления.
5. Определить, получена ли страница входа, checkpoint, сообщение об ограничении или содержимое профиля.
6. Проверить признаки соответствия контента запрошенному ID/URL.
7. Сформировать достоверный статус.
8. Показать результат в таблице.

Если обычный HTTP-запрос не даёт содержательных данных из-за динамической загрузки страницы, исследовать допустимую загрузку публичной страницы через изолированный браузерный процесс Electron.

Не использовать импортированные чужие сеансы, пароли, cookies или токены. Не обходить CAPTCHA, checkpoint и другие защитные механизмы.

## 12.4. Статусы

Использовать:

- `PROFILE_VISIBLE` — содержимое целевого профиля подтверждено;
- `LOGIN_REQUIRED` — требуется вход;
- `CHALLENGE_REQUIRED` — требуется проверка;
- `RATE_LIMITED` — ограничение запросов;
- `UNAVAILABLE` — страница явно недоступна;
- `NETWORK_ERROR` — ошибка сети;
- `UNKNOWN` — недостаточно данных;
- `CANCELLED` — проверка отменена.

Не утверждать, что аккаунт заблокирован, только потому, что публичная страница недоступна.

## 12.5. Интерфейс

Для каждой цели выводить:

- ID;
- нормализованный URL;
- результат;
- описание причины;
- дату проверки;
- имя и изображение, если получены из разрешённого и достоверного источника.

Добавить повторную проверку конкретной строки.

Сохранить массовую проверку до 100 целей, ограничение скорости и отмену.

## 12.6. Проверки

Обязательно проверить:

- доступный публичный профиль;
- страницу входа вместо профиля;
- checkpoint;
- HTTP 403/404/429;
- тайм-аут;
- перенаправление;
- некорректный ID;
- ошибку сети;
- 100 целей;
- отмену;
- повторный запрос.

Использовать контролируемые тесты и отдельно — разрешённые реальные публичные цели.

Если реальная проверка недоступна в CI, отметить её BLOCKED. Не объявлять Facebook Checker полностью исправленным только по имитационным ответам.

# 13. CLASSIFIER — восстановить распознавание важных полей

**Приоритет P0.**

## 13.1. Проблема

Классификатор не определяет часть данных, которые реально присутствуют во входных TXT.

В частности:

- Facebook ID;
- пароль;
- пароль почты;
- резервная почта;
- ФИО;
- GEO;
- дата рождения.

Необходимо исправить алгоритм распознавания и связывания полей.

## 13.2. Сохранить основной контракт

Не менять существующие основные поля:

- fullName;
- accountId;
- password;
- emailPassword;
- email;
- birthDate;
- geo;
- userAgent;
- token;
- cookies.

Дополнительно добавить отдельное поле `backupEmail`.

Резервную почту не путать с основной почтой или паролем почты.

## 13.3. Контекстное распознавание

Не полагаться только на регулярные выражения отдельных значений.

Реализовать анализ повторяющейся структуры в рамках одного файла.

Например, если в большинстве записей присутствуют похожие последовательности email, пароль, User-Agent, профильный URL и cookies, эта структура может использоваться для уточнения соседних записей.

Приоритет распознавания:

1. Явные названия полей.
2. Проверенная структура записи.
3. Формальные признаки значений.
4. Повторяющаяся структура нескольких записей.
5. Связь с идентификаторами внутри JSON и URL.
6. Ручное подтверждение при неоднозначности.

Учитывать, что пароли могут содержать произвольные символы и не имеют универсального формата.

Не назначать произвольную строку паролем только потому, что она расположена рядом с email.

## 13.4. Идентификаторы

ID определять по:

- явно указанному полю;
- URL `profile.php?id=...`;
- допустимому контексту Facebook;
- совпадающим значениям внутри структуры cookie.

Числовые значения хранить строками.

При конфликте идентификаторов выдавать предупреждение.

## 13.5. Резервная почта

Поддерживать варианты меток:

- backup email;
- recovery email;
- reserve mail;
- резервная почта;
- запасная почта;
- почта восстановления.

Если в записи несколько адресов почты без указания назначения, не выбирать случайно основной и резервный.

Использовать контекст и возможность ручного уточнения.

## 13.6. Даты и GEO

Распознавать разные допустимые форматы даты, включая `DD.MM.YYYY`, `D.M.YYYY` и ISO.

Проверять реальные календарные даты.

GEO распознавать как по кодам стран, так и по названиям на русском и английском.

Не путать GEO с названием страны в ссылке, описании или техническом тексте.

## 13.7. Полнота распознавания

Использовать предоставленные пользователем примеры как основу для воспроизведения структурных ошибок.

Для тестирования заменить секреты синтетическими эквивалентами, сохранив реальные шаблоны, разделители и порядок полей.

Не устанавливать искусственное правило «95% записей обязательно содержат пароль».

Вместо этого измерять полноту распознавания на размеченных наборах, где заранее известно, какие поля действительно присутствуют.

Все ожидаемые и однозначно определяемые поля должны быть извлечены корректно.

# 14. CLASSIFIER — определять начало полезных данных

**Приоритет P0.**

## 14.1. Проблема

В начале TXT могут находиться служебные комментарии, заголовки, описания, сообщения продавца, условия и другой мусорный текст.

Классификатор ошибочно создаёт из этих фрагментов пустые записи.

## 14.2. Новая логика

Добавить отдельный этап выделения полезного содержимого файла.

Не считать каждый фрагмент текста отдельным профилем.

Определять начало структурированных записей по совокупности признаков:

- синтаксис email;
- идентификатор аккаунта;
- профильный URL;
- структура cookie JSON;
- User-Agent;
- повторяющаяся последовательность полей;
- другие признаки записи.

Не привязываться к конкретному языку служебного текста.

Поддерживать русские и английские комментарии.

## 14.3. Требования

- Не создавать пустые первые записи.
- Не смещать поля последующих записей.
- Не пропускать полезные записи без email, если у них присутствуют другие достаточные признаки.
- Не удалять комментарии из оригинального TXT.
- Сохранять точные границы полезных записей.
- Различать текст между записями и содержимое многострочного поля.
- Не объединять соседние аккаунты в одну запись.

## 14.4. Проверки

Создать тестовый файл:

- 10 строк мусорного текста;
- затем 20 корректных структурированных записей;
- несколько комментариев между записями;
- разное число пустых строк;
- разные разделители;
- одна многострочная запись.

Ожидается: 20 полезных записей, без искусственных пустых строк.

Количество полезных записей должно определяться по фактической структуре, а не по количеству переводов строки.

# 15. CLASSIFIER — раскрываемые cookies

## 15.1. Убрать текущую маскировку

В колонке Cookies не отображать `••••••••`.

Заменить маскировку компактной сворачиваемой строкой.

В закрытом виде показывать название поля и кнопку раскрытия, не выводя содержимое cookie.

## 15.2. Раскрытие

По нажатию пользователь видит полное исходное значение cookie выбранной записи.

Для длинных данных использовать прокручиваемый контейнер.

Не обрезать полный текст при раскрытии.

Не изменять порядок ключей, пробелы или исходную сериализацию при копировании.

## 15.3. Копирование

Кнопка Copy копирует точное полное значение cookie.

После успешного копирования:

1. Показать уведомление.
2. Автоматически закрыть раскрытую строку.
3. Вернуть интерфейс в компактное состояние.

Если копирование неуспешно, показывать ошибку и не сообщать об успехе.

## 15.4. Безопасность

Не выводить cookies в логи.

Не загружать их во внешние сервисы.

Не использовать для авторизации.

После переключения записи или выхода из классификатора закрывать раскрытые секретные поля.

Привязку к конкретному record ID сохранять при фильтрации, сортировке и пагинации.

# 16. ARCHIVE — исправить сохранение записей

**Приоритет P0.**

## 16.1. Проблема

Пользователь сохраняет запись из классификатора, но она не появляется в Архиве.

Необходимо воспроизвести проблему и исправить весь путь данных.

## 16.2. Проверить

- действие Save / Archive;
- подтверждение классификации;
- формирование архивируемых полей;
- IPC;
- запись в SQLite;
- создание архивного файла;
- обновление списка;
- повторное открытие;
- восстановление после перезапуска;
- поведение при частично распознанной записи.

## 16.3. Требуемое поведение

После сохранения:

1. Выполняется фактическая запись.
2. Проверяется успешное завершение операции.
3. Обновляется представление Архива.
4. Новая запись становится доступной в Архиве.
5. Пользователь получает уведомление об успешном сохранении.
6. Запись остаётся доступной после перезапуска приложения.

Если требуется перемещение из текущей рабочей области, удалять её оттуда только после подтверждённого сохранения.

Исходный TXT-файл не удалять.

## 16.4. Обработка ошибок

Не показывать успех при ошибке SQLite или файловой системы.

Проверять:

- отсутствие доступа к каталогу;
- ошибки записи;
- коллизию имени файла;
- повреждённые данные;
- прерывание операции;
- повторное сохранение;
- перезапуск после сбоя.

Нельзя терять пользовательские данные при неуспешной архивации.

## 16.5. Обязательный тест

Сценарий:

**Импорт TXT → классификация → выбор записи → сохранение → открытие Архива → проверка значений → перезапуск BLEGO → повторное открытие той же записи.**

Результат должен быть PASS на установленном приложении.

Сохранить прежний семипольный контракт архива и не включать в него cookies или токены без отдельного согласования.

# 17. METAPAINTER / PHOTOS — исправить отображение карты

**Приоритет P0.**

## 17.1. Проблема

В разделе MetaPainter / Photos карта не прорисовывается должным образом.

## 17.2. Требуемый результат

Пользователь должен видеть интерактивную карту с географическим контекстом, а не пустую область или только абстрактные точки.

Карта должна показывать:

- территорию;
- границы выбранного города;
- картографическую подложку при доступности разрешённого источника;
- исходные GPS-точки;
- новые GPS-точки;
- выбранную фотографию.

## 17.3. Техническое решение

Проверить:

- создание и размер контейнера карты;
- инициализацию компонента;
- ошибки JavaScript;
- проблемы Canvas;
- изменение размеров при скрытых/открытых вкладках;
- разрешения и сетевые ограничения Electron;
- доступность картографических ресурсов;
- обработку загрузки и ошибок.

Рассмотреть внедрение MapLibre GL JS с подходящим поставщиком картографических данных.

Не использовать внешние серверы с нарушением лицензии или ограничений использования.

## 17.4. Онлайн и офлайн

При доступном разрешённом источнике отображать полноценную подложку карты.

При отсутствии интернета:

- показывать доступные локальные границы;
- показывать координатную сетку и маркеры;
- информировать, что фоновая карта недоступна;
- не блокировать экспорт фотографий.

Не передавать фотографии, cookie, пользовательские секреты и полные метаданные поставщику карты.

## 17.5. GPS-маркеры

После загрузки фотографий показывать исходные координаты.

После генерации новых координат — новые точки.

Сохранить переключатель:

**До / После**

Добавить:

- подсветку выбранного изображения;
- выбор точки;
- миниатюру;
- название файла;
- отображение координат;
- группировку близких маркеров;
- масштабирование;
- перетаскивание отдельной точки, если это поддерживается текущим контрактом редактирования.

## 17.6. Генерация GEO

Сохранить ранее утверждённое правило:

**Координаты случайно распределяются по всей территории выбранного города.**

Не возвращать настройки радиуса, минимального или среднего разброса.

Все точки должны оставаться внутри проверенных географических границ.

При отсутствии границ города не выдавать фиктивные координаты.

## 17.7. Проверка

На установленной сборке macOS:

1. Открыть Photos.
2. Загрузить 20 изображений.
3. Прочитать исходный GPS.
4. Открыть карту.
5. Убедиться, что карта визуально прорисована.
6. Выбрать страну и город.
7. Сгенерировать новые координаты.
8. Проверить переключатель «До / После».
9. Убедиться, что маркеры совпадают с планом изменений.
10. Экспортировать 20 копий.
11. Повторно прочитать записанные GPS-координаты.
12. Убедиться, что исходные фотографии не изменились.

Создать снимки экрана с реальной прорисованной картой.

Пустой Canvas не считать успешной проверкой.
